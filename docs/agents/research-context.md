# 产品开发如何使用 Input 研究成果

本文件由根目录 AGENTS.md、开发入口及工单操作规则共同引用。接手未完成工单、实现或评审产品改动时执行；不维护第二份工单状态表。

## 开工顺序

1. 读取当前工单、相关依赖及现有实现，确认哪些要求尚未完成。产品范围以用户当前指令、已批准规格和当前工单为依据；研究提供兼容性证据，不自行扩大范围。
2. 读取[业务架构](../input-architecture.md)的范围、证据表及工具局限，再依照下表选读相应章节、[候选协议](../protocol-candidates.md)和[模块契约](../module-contracts.md)。首次做相关模块的任务应读完模块契约。
3. 动手前说明相关结论如何影响本次实现或测试；不适用时写出理由。发现研究、规格和现有实现冲突时，核对来源与版本，不能默默选一边或把旧观察当成新验收。
4. 完成后在交付说明中留下下面的证据记录。对兼容行为做适用的合成夹具、异常路径和集成验证；缺少实机证据时保留缺口，不据此宣称硬件能力完成。

## 证据边界

- 本轮研究是本机 Input 1.1.0 安装包的静态分析。IA 编号不是固件验收编号，也不是自动工具证明了全部调用关系。固件 0.6.3 的既有实测只支持其实际测试过的内容。
- [分析设计](../designs/input-protocol-reconstruction.md)是计划，不是已实现功能清单；没有运行的 Hook、符号执行、场景或自动验收不能报告为完成。
- `node-hid` 的缓冲区布局不能直接当成 IOKit/Rust 后端的总线布局；候选写入方法、事务 API、范围默认值均需要各自证据。普通发送链没有事务调用，不代表存在固件级回滚。
- 原 Input 的本地失败回退不等于硬件恢复；Profile 选择可能触发同步。设备写入、宿主执行及映射恢复遵守当前任务授权与项目设备操作规则。
- 原始安装包提取物、个人配置与日志留在受忽略的 `.scratch/input-study/`，不进入代码、工单或提示词。独立实现使用整理后的协议说明及脱敏合成向量，不复制原应用或无许可 SDK 的实现。
- 其他机器缺少原始材料时仍可阅读上述已跟踪文档；需要核验源文件的结论标记为“原始来源未在本环境复核”。不要伪造复核结果或把缺少原件理解为可以忽略研究。

## 每项交付的证据记录

在现有交付或 PR 说明中加入三项即可，无需额外创建报告：

- **参考**：文档路径、相关 IA 编号；无关任务说明不适用理由。
- **影响**：采用了什么行为约束，落实在哪个实现或测试；若不采用，解释依据或冲突。
- **验证**：实际执行的检查及结果；哪些仅有静态依据，哪些已做实机验收，剩余缺口是什么。

评审时检查这三项与实际改动一致。只有引用而没有落实的相关约束不能算完成；也不能要求与本工单无关的全部研究都实现后才交付。

## 可直接使用的接续提示词

```text
请继续 Micro Input 当前尚未完成的产品开发工单。先读取仓库 AGENTS.md、README.md、docs/development.md、lessons.md，并执行 docs/agents/research-context.md。

查询工单的当前状态和依赖，结合已有代码确定剩余工作，不重复实现已经完成的功能。先核对 docs/input-architecture.md 的证据表与局限，按本次功能选读 docs/protocol-candidates.md、docs/module-contracts.md 及既有规格。说明相关 IA 证据对本次实现和验证的影响，然后在现有 Rust 核心 + SwiftUI 架构内完成实现与适用验证。

Input 1.1.0 的静态发现是兼容性证据，不是当前设备已通过验收的证明。保持原有映射和未知字段，区分本地草稿、设备状态与宿主动作；设备写入和宿主执行遵守当前授权。发现冲突时核对版本与来源，不默默覆盖已批准规格。

交付时列出“参考证据、实现影响、实际验证与剩余缺口”。如拆分任务或交接，将 docs/agents/research-context.md、相关证据编号和适用限制一并传递。无需为已授权的常规实施步骤重复询问。
```

## 生效范围

这些规则随仓库版本传递：从包含本文件及对应 AGENTS.md 修改的 checkout 开始工作，Agent 开工即可发现入口。旧 worktree、旧分支和已运行的会话不会自动刷新；交接前同步这些文档，或向现有会话发送上面的提示词。提示词不能替代缺失文件，跨环境交接须带上已跟踪的研究文档；完成同步前不宣称接入已生效。
